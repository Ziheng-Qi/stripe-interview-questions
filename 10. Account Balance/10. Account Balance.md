### 第一轮 Coding：Account Balance 变体题

实现一个系统，处理用户间的转账记录，目标是让所有账户余额最终为 0。

其实这题和 LeetCode 上的“最少交易次数”那题挺像的，但好在 Stripe 并不要求你写出最优解，只要功能实现正确、逻辑清晰就可以了。我的实现重点在于能跑通一组账户交易后，余额最终能调平。至于是否最优，面试官并不强求。

面试官随后提了两个 Follow-up，我也简单说说当时怎么答的：

**Follow-up 1：如何实现最少交易次数？**

我当时没写代码，而是讲了解法思路。可以从贪心或 DFS 两个角度入手：

**贪心解法**：将账户分成正负余额两组，尽可能让“最大债主”匹配“最大债务人”，一笔笔清掉。

**DFS + 剪枝**：尝试所有可能的交易路径，并用剪枝来优化搜索空间，从而找出交易次数最少的方案。

只要思路讲得明白，面试官不会强求你把代码写出来。这个思路好像说的不太对吧？

**Follow-up 2：如何审计（audit）整个交易过程？**

我第一反应就是从“日志 + 校验”两个维度回答：

**交易日志记录**：每次交易都打 log，包括交易 ID、金额、账户余额和时间戳；

**校验逻辑**：检查每笔交易前后账户余额总和不变；

**交易链路跟踪**：通过交易 ID 建立起整个交易流程的链路，方便事后追溯；

**异常检测**：监控是否有大额异常交易、循环交易等不合规情况。

最后我还补了一句，实际场景中这种系统应该有事务控制和数据一致性校验机制，防止边界 case 出问题。


1. **End-to-End Tracing**
    
    Tag every API call, background job and webhook with a Correlation-ID and capture spans via OpenTelemetry/Jaeger so you can reconstruct each payment’s lifecycle (charge.succeeded → payment_intent → balance_transaction → Ledger Entry).

"""
**“Capture spans”** means recording each significant operation or step within a transaction lifecycle as a **span** using a distributed tracing system like **OpenTelemetry** or **Jaeger**.

A _span_ represents a single unit of work — for example, an API call, a webhook handler, or a background job.

By tagging these spans with the same **Correlation-ID**, you can reconstruct and visualize the **end-to-end flow** of a payment across different services or systems, which is essential for debugging and auditing.

Example:
> If a customer makes a payment, you might capture one span for the payment_intent creation, another for the webhook handler that updates your database, and a third for the background job that reconciles the ledger entry.

"""

2. **Immutable Event Log & Idempotent Webhooks**
    
    Persist every Stripe event (charge.succeeded, payment_intent.*, balance_transaction.*, etc.) into an append-only store (Kafka/ELK) and verify+dedupe by event.id + correlation-id to guarantee no double-count or loss.
    
3. **Automated Reconciliation (/ˌrekənsɪliˈeɪʃ(ə)n /) & Alerts**
    
    Run a nightly job that compares your internal order/refund totals against Stripe’s balance_transaction API for the same period. Generate a discrepancy report and trigger pager alerts if mismatches exceed thresholds.
    
4. **Replay & Compensation Mechanism**
    
    Provide tooling or CLI  to re-fetch missing Stripe events or replay your own logged events, and automatically reconcile “stuck” transactions without manual database hacks.
    
5. **Double-Entry Ledger & Compliance**
    
    For compliance and financial accuracy, we convert each Stripe balance transaction into clear debit and credit entries using a double-entry system. These records are stored in a way that ensures they can’t be changed once written, which helps with audits and security. We also make sure that only the right people have access, and we keep these logs for a few years to meet industry standards like PCI-DSS **(Payment Card Industry Data Security Standard, 一套关于处理信用卡数据的安全标准，确保商家安全地存储、处理和传输持卡人数据)**.
