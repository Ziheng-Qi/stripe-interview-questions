# 23. Incident Monitor — Transaction Alert Trigger / Resolve

> **来源**：一亩三分地题库。频率 Medium，最近一次 2026-09-07，出现在 OA、tech screen 和 phone screen 里。
> 代码：同一文件夹里的 `incident_monitor.py`

## 题目

```
Implement detect_incidents(logs) and return every alert event produced while processing the log.

Each input string: timestamp,merchant_id,status_code,count
  - timestamp: integer seconds
  - status_code: 200 = success, 4xx client error, 5xx server error
  - count: number of transactions with that outcome for the merchant at that second
  - input is valid, sorted by timestamp, no duplicate (timestamp, merchant_id, status_code)

Evaluate each arriving log against a 30-second sliding window, defined as [T-29, T] inclusive.
Each alert belongs to one (merchant_id, error_status_code) pair; a merchant can have several
active alerts. Do not emit a duplicate TRIGGER while an alert for the same pair is active.

Part 1 - TRIGGER when at least 5 failures with the same error code occur for the same merchant
         inside the current window.
Part 2 - Trigger only when BOTH hold inside the window:
           - at least 5 failures with that error code
           - those failures are STRICTLY more than 1% of the merchant's successful volume
             (total count of status 200 in the same window)
Part 3 - An active alert becomes RESOLVE when a new log for THAT merchant arrives and the window
         no longer meets the Part 2 conditions. A time gap with no logs changes nothing.
         A resolved pair may trigger again later.

Output strings: timestamp,event_type,merchant_id,status_code
Sorted by timestamp, merchant id, status code, event type (RESOLVE before TRIGGER on a full tie).

Part 1 example
  10,merchant1,500,2 / 10,merchant2,500,1 / 15,merchant1,500,2 / 20,merchant1,500,1 / 20,merchant2,500,4
  -> 20,TRIGGER,merchant1,500
     20,TRIGGER,merchant2,500

Part 2 example
  10,merchant1,200,600 / 12,merchant1,500,6 / 15,merchant2,200,599 / 16,merchant2,500,6
  -> 16,TRIGGER,merchant2,500        (6 is exactly 1% of 600 -> not strictly more)

Part 3 example
  10,merchant1,500,6 / 16,merchant2,500,6 / 45,merchant1,200,1 / 46,merchant2,200,1
  -> 10,TRIGGER,merchant1,500
     16,TRIGGER,merchant2,500
     45,RESOLVE,merchant1,500
```

## 一个坑：窗口边界

题面写的窗口是 `[T-29, T]`，但 Part 3 的例子里，46 秒时 16 秒那条日志（正好 30 秒前）仍然算在窗口内，所以 merchant2 没有 RESOLVE。照文字定义的话，46 秒应该多输出一行 `46,RESOLVE,merchant2,500`。题库也特意提醒了这个矛盾。

代码里只用一个常量 `LOOKBACK` 控制这件事：
- `LOOKBACK = 30`（默认）：和例子一致，保留 `ts >= T - 30` 的日志。
- `LOOKBACK = 29`：照文字定义。

**开写前先问清楚以哪个为准。**

## 思路

- **每个 merchant 一个滑动窗口**：日志放进 deque（先进先出），同时维护 `counts[status_code]` 累加值。过期出队时减去它当初加进来的数，这样加和减永远对得上。
- **同一秒的日志先全部加进窗口，再做判断**，免得同一秒内一会儿触发一会儿解除。
- **只重新评估这一秒有日志的 merchant**：题目说 resolve 由该 merchant 自己的流量驱动，没有新日志就不变。要评估的错误码 = 窗口里现有的错误码 ∪ 这个 merchant 正在报警的错误码。
- **状态机**：用 `active` 集合存 `(merchant, code)`。条件从假变真就 TRIGGER，从真变假就 RESOLVE；状态不变就不输出，所以不会重复触发。
- **"严格大于 1%" 用整数比较**：`failures * 100 > successes`。没有成功交易时，`successes = 0`，只要有 5 次失败就成立。
- **最后统一排序**：按 `(ts, merchant, code, event)` 排，RESOLVE 按字母序自然排在 TRIGGER 前面。

## 开写前要问的

- 窗口下边界是 T-29 还是 T-30（见上面）？
- 题目是逐个 part 解锁，还是三个要求一开始就都给了？题库提到有少数情况是一次性全给。
- 除了 200 以外，其他 2xx / 3xx 算成功还是失败？
- 同一秒有多条日志时，是一起评估还是一条一条评估？
